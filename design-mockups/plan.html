Working conventions (read before any task)

These rules apply to every task in this plan. If a task contradicts them, the convention wins unless the task explicitly overrides it.

  1. One task = one commit. Use the task ID in the commit message subject, e.g., DP-01: brand mark in admin nav. Write a short body explaining what changed and why.
  2. Read the whole task card before touching code. Confirm the file list matches what you find in the repo. If a file the task references doesn't exist or has changed, stop and re-read the plan rather than guessing.
  3. Stay inside the task spec. Don't refactor unrelated code, don't rename things, don't introduce new abstractions, don't add features that aren't called out. Three similar lines is better than a premature abstraction.
  4. Don't add dependencies without explicit user approval. The stack is Next.js 14 + React 18 + firebase + firebase-admin + nodemailer + dotenv + tsx. Stick to it. No Tailwind, no UI libraries, no state management libs.
  5. CSS goes in app/globals.css. The app uses plain CSS — add new classes, don't rewrite existing ones unless the task says so. Follow the existing token system (--bg, --panel, --green, etc.).
  6. TypeScript must compile cleanly. Run npx tsc --noEmit before committing. No any types without a good reason. No // @ts-ignore.
  7. ESLint must pass. Run npm run lint before committing.
  8. Test in dev locally. Run npm run dev and visit the affected routes (/, /admin, etc.) before marking a task done. For backend changes, exercise the form end-to-end.
  9. Never deploy without explicit user permission. vercel and firebase deploy are user-triggered only.
  10. Never commit secrets. Keys live in .env.local (gitignored). If you need a new env var, document it in .env.local.example with a placeholder.
  11. When unsure, ask the user. Specifically: brand assets, profanity word list contents, production URLs, custom domain, and anything labeled "Open question" in this plan.
  12. Existing code is the reference for style. Look at components/admin/ReviewQueue.tsx and app/page.tsx for the React style; look at lib/firestore.ts and lib/utils.ts for the helper-function style. Match it.
  13. No comments in code unless the WHY is non-obvious. Don't restate what the code does. The // ─── Section ──── divider comments in existing files are fine; follow that pattern for new files.
  14. Don't create new docs. Don't write README updates, design rationale files, or migration guides unless the task explicitly asks for it. The plan is the doc.
!
Critical: If you find a task whose spec doesn't match what's in the codebase (e.g., a file path has moved, an API has changed, a function was renamed), stop and report back. Do not guess. The plan was written against a specific state of the codebase; drift is possible.
A2

Quality bar

A task is "done" only when all of the following are true:

  • Every acceptance criterion in the task card is satisfied.
  • npx tsc --noEmit passes (no TypeScript errors).
  • npm run lint passes (no ESLint errors).
  • The dev server (npm run dev) starts without errors and the affected pages render without console errors.
  • The feature works end-to-end in dev — for form changes, submit a real test entry; for admin changes, sign in and verify the change is visible.
  • No console.log calls left in production code paths (server-side console.error for caught exceptions is fine).
  • No secrets committed (check git diff before commit).
  • The commit message starts with the task ID.

FU-01 Profanity word list + regex check functional high medium

Goal: Build the moderation primitive — a curated word list + a function that returns matched terms for any given text. Used by FU-02 and FU-03 to flag risky submissions.

Files

lib/moderation.tsNEW. Exports PROFANITY_LIST (string[]) and checkProfanity(text: string): string[].

Spec

checkProfanity takes a string, normalizes (lowercase, strip punctuation), splits into tokens, and returns any tokens that match the word list. Returns an empty array if clean.

FU-04 Rate limiting on /api/submit functional high medium

Goal: Cap how often a single IP can submit. Cheap insurance against spam waves. Reject with HTTP 429 when exceeded.

Files

app/api/submit/route.tsAdd a rate-limit check before validation. Read client IP from request headers (x-forwarded-for on Vercel).
lib/rate-limit.tsNEW. Exports checkRateLimit(ip: string): Promise<{ ok: boolean; resetIn?: number }>. Implementation uses Firestore as the store (lasts across cold starts).
firestore.rulesAdd a rule for rate_limit/{ip} — server-only (no client read/write).

Spec

Limits: 3 submissions per IP per 60 seconds, 30 per IP per hour. Reject with 429 (and a JSON body explaining the limit) when exceeded.

Firestore doc shape for rate_limit/{ip-hash}:

{ timestamps: number[], // recent submission unix-ms, last 60 entries max updatedAt: Timestamp }

Algorithm:

  1. Hash the IP (e.g., SHA-1) to avoid storing raw IPs.
  2. Read the doc. If missing, treat as empty.
  3. Filter timestamps to those within last hour. Count.
  4. Reject if count exceeds hourly limit, or if last-minute count exceeds minute limit.
  5. Otherwise: append Date.now() to the array, write back (capped at 60 entries).

Acceptance

  • Submit 4 suggestions from the same browser within 60s — the 4th gets HTTP 429 with a body like {"error": "Too many submissions. Try again in N seconds."}
  • Submit at a steady cadence (one every 30s) — none are rate-limited
  • Firestore rate_limit/{ip-hash} doc is created/updated on each submission
  • IPs are hashed, not stored raw (privacy hygiene)
  • Rules deny client reads/writes to rate_limit/* — only admin SDK can touch it
  • The form's existing error display shows the 429 message to the user

Watch out for

  • IP comes from request.headers.get('x-forwarded-for') — first value if comma-separated. Firebase App Hosting proxies the same header.
  • Don't use an in-memory map for storage — Vercel functions are stateless and can scale horizontally. Firestore is the right store here.
  • Don't block the request waiting on the Firestore write for the timestamp append. Read for the check (must await), then write fire-and-forget after responding.
